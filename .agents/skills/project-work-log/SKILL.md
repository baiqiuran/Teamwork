# 日序工作日志

## 数据来源

本技能所在目录向上三层为应用仓库根目录。默认只读取该 Git 仓库；用户指定其他项目或数据来源时按其要求处理。工作区布局遵循已加载的 `AGENTS.md`；没有独立工作区约定时，以应用仓库根目录作为工作区根目录。

1. 优先使用用户提供的工作内容或提交记录，保留其指定的日期、项目与范围。
2. 未提供工作内容时，从应用仓库读取目标日期范围内的提交。日报默认当天，周报默认本周截至当天；日期与查询边界的时区使用当前用户上下文。
3. 默认读取各仓库的 `git config user.email`，按作者邮箱精确筛选本人提交。用户明确要求全部提交时才汇总全部作者；邮箱缺失时先询问作者范围。
4. 多个指定仓库的查询可以并行，按项目分组并跳过空结果。提交说明不足以判断功能时，查看相关变更或验收记录，区分已实现、已验证与待完成事项。
5. 没有可核实的工作内容时，说明查询范围与空结果，向用户收集补充信息后再生成日志。

## 业务术语

生成前读取唯一术语正文 [CONTEXT.md](../../../CONTEXT.md)。本工作区的项目业务名称使用“日序”，模块与功能名称沿用术语正文；需要解释业务行为时读取相关 [ADR](../../../docs/adr/)。

用户指定其他项目时，优先遵循该项目的领域文档约定；没有约定时查找 `CONTEXT.md` 或 `docs/domain.md`。项目与事项均使用业务名称。术语缺失时优先采用用户提供的名称，再退回目录名，并仅在对话中提示缺失。

## 总结与明细

生成两个版本，所有条目使用业务语言描述实际功能、影响范围或用户价值。

### 总结

用 1–3 条概括最有业务价值的工作，优先保留用户可见的新功能、线上缺陷修复、性能与稳定性改善。每条以“新增、修复、优化、重构、完善”等具体动词开头，直接说明做了什么与带来的价值，省略技术实现细节。

### 明细

按项目与模块归并同类事项，每条以具体动词开头。功能开发、缺陷修复、优化与重构分别表达，数量作为补充，重点写实际功能点。

默认全部按编码事项处理，直接在 `【项目名称】` 下列事项。用户明确标注业务事项时，才在对应项目下分别列“业务：”和“编码：”，业务在前；只列实际存在的分组。

总结与明细合计 150–350 字，含中英文字符与标点，不含空白与 Markdown 符号。不足时补充已有依据支持的业务背景、影响范围或关键场景；超过时合并同类事项，保留高价值内容，总结最多 3 条，明细每个项目最多 4–5 条。资料不足以支撑 150 字时如实保留短版并在对话中说明，不为凑字数编造工作。

总结与明细之间直接衔接，不添加分隔线。

## 保存与展示

默认保存到工作区根目录的 `.scratch/work-logs/`，目录不存在时创建：

- 日报：`工作日志-YYYY-MM-DD.md`。
- 周报：`工作周报-YYYY-MM-DD至YYYY-MM-DD.md`，日期为本次汇总区间。
- 同一目标文件已存在时覆盖，视为重新生成。
- 用户指定输出路径或要求仅在对话中展示时，按其要求处理。

文件内容按下列结构保存，日期或区间与本次查询一致：

```markdown
# 工作日志 YYYY-MM-DD

## 总结

1. ……

## 明细

【日序】

1. ……
```

周报标题使用“工作周报”与汇总区间。保存后在对话中展示相同的总结、明细与文件链接；查询限制、资料不足或术语缺失的提示仅在对话中给出。

用户另行要求在日序中保存草稿或提交日报时，加载可用的 `daily-flow` 技能完成相应操作；本技能负责生成内容，本地日志保存本身不执行这些操作。
